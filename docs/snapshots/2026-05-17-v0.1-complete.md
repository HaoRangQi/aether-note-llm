## 4. 决策与权衡（**接手者必读**）

这一节记录"为什么是这样"，避免后来人误以为某个选择是随便定的。

### 4.1 为什么先做 Obsidian Plugin 而不是独立 Tauri 应用？

设计阶段我们考虑过三种形态：纯桌面 Tauri / Plugin / Hybrid。最终选 Plugin 因为：

- **编辑器复用** — Obsidian 已经是市面上最好的 markdown 编辑器之一，自己造没必要
- **上市时间** — Plugin 几周，Tauri 应用几个月
- **零数据锁定** — 所有数据都是 vault 里的 markdown，用户随时能离开

但**核心代码不依赖 Obsidian**：业务逻辑全在 `@aether/core`，通过 `IHostAdapter` 跟外界通信。未来要做 Tauri 应用就是再写一个 `TauriHostAdapter`，core 零修改复用。

### 4.2 为什么 `embedding` 单独设 Feature Binding？

OpenAI 兼容协议下，**chat 和 embedding 是两个不同 endpoint，可能要用不同模型甚至不同 Provider**：

- DeepSeek 有便宜的 chat（`deepseek-chat`），没有 embedding 模型
- SiliconFlow 提供 `BAAI/bge-m3` embedding，但用户也许更喜欢 OpenRouter 的 chat 路由

把每个 Feature 独立绑定，用户能任意组合。代价是配置略繁琐 —— 通过"最少配置 embedding + inbox_metadata 就能跑"来缓解。

### 4.3 为什么 alpha 升高时偏向 BM25（不是向量）？

alpha 是**文本权重**。语义清晰看 `final = α × text + (1-α) × vector`。

当索引大量 stale（用户切换 embedding 模型后）时，向量结果不可信 → SearchEngine 自动**升高** alpha 到 0.8，更依赖 BM25。

这一条最初在 spec 自审里写反过一次（"降到 0.2"），已经在 `6d20abb` 修了。如果将来再调阈值，注意是"stale 越多 alpha 越高"。

### 4.4 为什么 inbox 默认不自动拆分大文档？

最初设计有"AI 把一篇大文档自动拆成多篇 inbox 卡片"。自审时砍掉了，因为：

- LLM JSON 输出可靠性不够，会成为 MVP 阻塞点
- 用户更需要的是"导入这一篇就是一篇"+ 之后**主动**对长文做拆分

所以 v0.1 是**整篇入库**。"拆分这一篇笔记" 留给 v0.2。

### 4.5 为什么覆盖率阈值是 65/55 不是 70/60？

`OramaIndexStore` 依赖 orama 内部行为，branches 难以高覆盖（错误路径主要靠 orama 自己抛）。先把阈值定保守，实测达到 80% branches → CI 阈值依然 55，留出修改空间。v0.2 目标提到 70/60。

### 4.6 为什么 CI 里要先 `pnpm --filter @aether/core build` 再 typecheck？

Plugin 通过 workspace 引 `@aether/core`，但 `@aether/core` 的 `exports` 指向 `dist/index.js` / `dist/index.d.ts`。干净 checkout 上 dist 不存在 → plugin typecheck 报 "Cannot find module"。

这一条**踩过坑修过**（commit `49bb21c`）。release-checklist 也单独标注了这个顺序。

### 4.7 为什么 `aether_id` 是 optional 的？

设计阶段决策：**Aether 创建的笔记**带 `aether_id`，**用户原有的笔记**没有。后者用 `vaultPath` 兜底作为身份。这样：

- 不强迫用户接受"插件修改我的所有笔记 frontmatter"
- 但提供了"用户主动让 Aether 接管这篇笔记"的升级路径

代码里看 `indexExistingVaultFile()`：`id = fmId ?? \`path:${vaultPath}\``。

### 4.8 为什么把 main.js 也提交进 git？

Obsidian 社区插件惯例 —— GitHub release 的 asset 是从主分支拉 `main.js`。每次发布前 build 一次再 push tag。这跟"build 产物不进 git" 的 web 工程惯例相反，但对 Obsidian 插件分发是必要的。

## 5. 没做的事 / 已知限制

### 5.1 真实场景从未跑过

**v0.1 没有装到任何一个有真实笔记的 vault 上跑过**。所有验证都是 mock provider + InMemoryHostAdapter。

可能在真实场景才会暴露的问题（**接手者第一件事应该是手测**）：

- requestUrl 调真实 OpenAI 兼容端点的兼容性（已知不同厂商 SSE 格式略有差异）
- 大 vault（>1000 笔记）下 orama 内存占用与启动时间
- Notion ZIP 真实导出包的边界（含 attachments 文件夹、嵌套数据库等）
- Chrome 书签 JSON 真实文件的大小与解析性能
- iOS / Android 移动端 Obsidian 上能否正常加载

### 5.2 v0.1 显式不做的（出现在设计 §0 非目标）

- ❌ 完整 AI 聊天面板（Cherry Studio 那种）
- ❌ 实时 inline suggestion（Cursor 式陪写）
- ❌ 协同 / 分享
- ❌ 云同步（用户用 iCloud / Syncthing / Obsidian Sync 自行解决）
- ❌ 移动端独立打包（复用 Obsidian 移动端）

### 5.3 v0.2 路线图已记但未做

详见 `docs/superpowers/specs/2026-05-16-aether-note-llm-design.md` §11：

| v0.2 候选                                | 备注                                      |
| ---------------------------------------- | ----------------------------------------- |
| RAG 综合回答                             | 搜索页 "AI 综合回答" 按钮已在 UI 中预留位 |
| "智能拆分这一篇" 高级功能                | 入口设想：右键已有笔记 → "Aether: Split"  |
| Obsidian vault 导入                      | 一个 vault 复制到另一个 vault             |
| Anthropic / Gemini 原生 SDK              | 当前只有 OpenAICompatible 一个适配器      |
| 浏览器扩展（One-Click Save Web Article） | 后端已有 SourceConnector 接口可扩展       |
| 独立 Tauri 桌面应用                      | `IHostAdapter` 接口已经为此设计           |
| 多模态识别（图片 OCR）                   | InboxItem 已经有 `assets` 字段占位        |
| 移动端真实手测                           | manifest `isDesktopOnly: false` 已经允许  |

## 7. 项目背景与决策路径（**叙事**）

这一节是回忆性的，记录这一阶段是怎么走过来的，方便理解为什么有些设计是现在这样。

1. **起点**：用户提了一个非常大的愿景 —— "个人数字化管理器，文章/图片/音视频/书签/歌单都存起来，AI 掌握，对话调用"。
2. **范围分解**：直接做整个平台会失败。澄清后聚焦到**知识检索 + 书签召回**这两个最痛的点。多模态、推荐系统、跨资产关联推到未来。
3. **形态选型岔路**：用户最初接受了 Tauri 桌面 + 自托管 web 方案；自审阶段发现 Obsidian Plugin 路线投入 1/10 拿到 80% 价值，转向 Plugin。这次方向调整发生在设计已经写到 11 节之后，spec 全部重写过。
4. **设计自审**：spec 写完后自查发现 5 处问题（α 语义矛盾、RAG 边界口径不一、身份策略缺失、索引扫描范围矛盾、编号重复），都修了。
5. **实施计划自审**：plan 写完后换视角审查发现 9+ 个 P/Y 级问题（chunker 双实现、字段冲突、动态 import、测试入口 hack、覆盖率阈值不切实际等），全部修订到位再开始动代码。
6. **实施过程**：30 个提交从空目录到完成，**只有两次失败需要回头修**：
   - slugify 把空格当保留字符吞了（regex 写错）
   - chat 函数用 body 存在性判断流式分支 → 改为按 Content-Type 判断
     两次都是几分钟修完。
7. **CI 真实跑过一次发现的隐患**：本地 typecheck 通过是因为 build 缓存还在；干净 checkout 上 CI 会失败。在 `49bb21c` 加上 "先 build core" 步骤修了。**这种"我以为通了但其实没通"的 bug 是最容易溜过去的**。
8. **端到端冒烟脚本**：用户问"启动看看"时意识到 plugin 层除了手测之外缺一个能跑的入口，写了 `packages/core/scripts/smoke.mjs`，10 步覆盖完整业务流。这一份现在也是 release-checklist 的必跑项。
9. **启动指南**：用户说"写成文档落在项目里面，别人才能看懂"，加了 `docs/contributing/getting-started.md`（350+ 行）+ README 顶部最显眼入口。

整个流程是 brainstorm → spec → plan → 自审 → 实施 → release 准备 这一套**标准产品工程流水线**走了一遍。可以作为这个项目未来 v0.2 / v0.3 的样板。
